Quick Start

Create a schema file and generate all 7 output formats in under 30 seconds:

1. Create api-spec.yml

apinox: "1.0"
name: my-api
version: 1.0.0
description: My first API
base_url: https://api.example.com/v1

auth:
  default: bearer
  schemes:
    - id: bearer
      type: http
      scheme: bearer
      header: Authorization
      prefix: "Bearer "

groups:
  - id: users
    name: Users

endpoints:
  - id: list-users
    name: List Users
    group: users
    method: GET
    path: /users
    responses:
      - status: 200
        description: Success
        examples:
          - name: default
            value:
              id: usr_1
              name: John Doe
              email: john@example.com

2. Validate

$ apinox validate api-spec.yml Check for errors

3. Build all formats

$ apinox build api-spec.yml -o ./dist Generate everything

4. See the output

dist/
├── docs/
│   ├── my-api.md                   # Markdown docs
│   └── my-api.scalar.html           # Interactive docs
├── hurl/
│   ├── my-api.hurl                  # Hurl test scripts
│   └── my-api.sh                    # Curl commands
├── insomnia/
│   └── my-api.insomnia.json         # Insomnia import
├── openapi/
│   └── my-api.openapi.yaml          # OpenAPI 3.1
└── postman/
    └── my-api.postman_collection.json # Postman collection

How It Works

Apinox uses a schema-first approach:

  1. Write — Define your API in YAML/JSON with endpoints, auth, parameters, and response examples
  2. Validate — Catch missing fields, duplicate IDs, broken references before generating
  3. Generate — Produce 7 output formats from a single source of truth
  4. Import — Convert existing OpenAPI/Swagger specs into Apinox schema
  5. Sync — Push generated Postman collections directly to your workspace

Schema Reference

The Apinox schema is the single source of truth for your API. It's a YAML (or JSON) file that describes every endpoint, parameter, authentication method, and response.

Root Fields

FieldRequiredDescription
apinox✓Schema spec version. Must be "1.0".
name✓API name. Used for output filenames.
version✓API version (e.g. 1.0.0, 2.4.0).
descriptionBrief description of the API.
base_urlDefault base URL for all endpoints (e.g. https://api.example.com/v1).
Example
apinox: "1.0"
name: atomix-cloud-api
version: 2.4.0
description: Atomix Cloud platform API
base_url: https://api.denisetiya.site/v1

Authentication

Define auth schemes globally. Endpoints can override or disable auth per-request.

FieldDescription
defaultDefault auth scheme ID applied to all endpoints (unless overridden).
schemes[]List of auth scheme definitions.

Auth scheme types:

TypeFieldsExample
http (Bearer) scheme: bearer, header: Authorization, prefix: "Bearer " JWT tokens
apiKey key: X-API-Key, in_location: header API key auth
basic scheme: basic Basic auth
oauth2 Custom fields OAuth 2.0 
auth:
  default: bearer
  schemes:
    - id: bearer
      type: http
      scheme: bearer
      header: Authorization
      prefix: "Bearer "
      description: JWT Bearer token
    - id: api_key
      type: apiKey
      key: X-API-Key
      in_location: header

Per-endpoint auth override:

endpoints:
  - id: public-endpoint
    auth: ~              # null = no auth required
  - id: admin-only
    auth: api_key          # use api_key scheme instead of default

Environments

Define multiple environments (production, staging, development) with different base URLs and variables.

FieldDescription
nameEnvironment name (e.g. production, development).
base_urlBase URL for this environment.
varsKey-value variables for Postman/Insomnia environments.
environments:
  - name: production
    base_url: https://api.example.com/v1
    vars:
      TOKEN: prod_token_value
  - name: development
    base_url: http://localhost:8520/v1
    vars:
      TOKEN: dev_token_local

Groups

Organize endpoints into logical groups. Groups appear as folders in Postman/Insomnia.

FieldDescription
idUnique group identifier.
nameDisplay name.
descriptionOptional description.
authOptional auth override for all endpoints in this group.

Endpoints

The core of the schema. Each endpoint describes a single API route.

FieldRequiredDescription
id✓Unique endpoint identifier.
name✓Human-readable name.
groupGroup ID this endpoint belongs to.
method✓HTTP method: GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS.
path✓URL path with optional {param} placeholders.
descriptionEndpoint description (supports multi-line |).
deprecatedMark as deprecated (true/false).
tagsList of tags for filtering.
authAuth scheme override (null = no auth, omit = use default).
path_paramsPath parameter definitions.
query_paramsQuery parameter definitions.
headersRequest headers.
bodyRequest body definition.
responsesResponse definitions (at least one recommended).
rate_limitRate limit info: requests + window.
serversPer-endpoint server URL overrides.
Important

Response examples must use examples: format with name and value. Do NOT use body: — it produces empty responses in generated output.

Path Parameters

Use {param_name} in the path and declare the parameter details:

path_params:
  - name: user_id
    type: string
    required: true
    pattern: "^usr_[a-zA-Z0-9]+$"
    description: User ID
    example: usr_abc123

Query Parameters

query_params:
  - name: page
    type: integer
    required: false
    min: 1
    max: 100
    default: 1
  - name: sort
    type: string
    enum: [asc, desc]
    default: asc

JSON body example:

body:
  type: json
  required: true
  schema:
    email:
      type: email
      required: true
      description: User email
    password:
      type: string
      required: true
      sensitive: true
      min_length: 8
    role:
      type: string
      required: false
      enum: [user, admin]
      default: user
  examples:
    - name: valid_user
      value:
        email: user@example.com
        password: SuperSecret123!

body:

      type: file
      required: true
      accept: [image/jpeg, image/png]
      max_size_mb: 5
      description: Avatar image file

      type: string
      default: square
      enum: [square, circle]

Responses

Define success and error responses with examples. Multiple response status codes per endpoint.

responses:
  - status: 200
    description: User found
    content_type: application/json
    headers:
      - name: X-RateLimit-Remaining
        description: Remaining rate limit
    schema:
      id:
        type: string
    examples:
      - name: success
        value:
          id: usr_abc123
          name: John Doe
  - status: 404
    description: Not found
    examples:
      - name: not_found
        value:
          error: not_found
          message: User not found

Error Patterns

Define reusable error responses to avoid repetition:

error_responses:
  patterns:
    - id: unauthorized
      status: 401
      description: Missing or invalid token
      example:
        error: unauthorized
        message: Authentication required
    - id: not_found
      status: 404
      example:
        error: not_found
        message: Resource not found

# In endpoints, reference via use_pattern:
endpoints:
  - id: get-user
    responses:
      - status: 200
        examples:
          - name: default
            value: { id: usr_1 }
      - status: 401
        use_pattern: unauthorized         # ← reuses error pattern
      - status: 404
        use_pattern: not_found

Modular Schema Includes

Split large APIs across multiple files. Useful for team workflows or organizing by domain.

# ── main.yml ──
name: enterprise-api
version: 3.0.0
apinox: "1.0"

includes:
  - path: ./includes/auth.yml
  - path: ./includes/users.yml
    prefix: /v3          # Prefix all endpoint paths
  - path: ./includes/orders.yml
# ── includes/users.yml ──
endpoints:
  - id: list-users
    method: GET
    path: /users
    responses:
      - status: 200
        description: OK

CLI Reference

Seven commands. One binary. Every command supports --help for detailed options.

Validate

Check your schema for errors before generating. Catches:

  • Missing required fields (name, version)
  • Duplicate endpoint/group IDs
  • Broken auth scheme references
  • Path-parameter mismatches ({id} in path but not declared)
  • Invalid HTTP methods
  • Unused auth schemes (warning)
  • Missing response examples (warning)
$ apinox validate api-spec.yml Text output (default)
$ apinox validate api-spec.yml --format json JSON output (CI-friendly)

Exit codes: 0 = valid (warnings OK), 1 = errors found.

Build

Generate output files from your schema. Can produce one format or all seven at once.

$ apinox build api-spec.yml All formats, output to ./dist
$ apinox build api-spec.yml -o ./docs -f postman Single format
$ apinox build api-spec.yml --skip-validate Skip validation (build anyway)

Format values: postman, openapi, markdown, scalar, insomnia, hurl, all (default).

Watch

Auto-rebuild your docs whenever the schema file changes. Uses filesystem notifications with 300ms debounce.

$ apinox watch api-spec.yml -o ./dist

Diff

Show changes between two versions. Uses changelog entries in the schema.

$ apinox diff api-spec.yml 1.0.0 2.0.0 Markdown output
$ apinox diff api-spec.yml 1.0.0 2.0.0 --format text Plain text output

Migrate

Generate a migration guide by comparing two actual schema files (not changelog entries).

$ apinox migrate api-v1.yml api-v2.yml
$ apinox migrate api-v1.yml api-v2.yml -o migration-guide.md

Import

Convert an existing OpenAPI 3.x or Swagger 2.0 spec into Apinox schema format.

$ apinox import swagger.json -o api-spec.yml

Postman Sync

Push generated Postman collections directly to your Postman workspace. Supports creating new collections or updating existing ones.

$ apinox sync api-spec.yml --postman-key PMAK-xxx --workspace wkspc_xxx --collection-name "My API"

Config file alternative — create .apinox.toml:

[sync.postman]
api_key = "PMAK-xxx"
workspace_id = "1a2b3c4d-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
collection_id = "clctn_xxx"

Then simply run: apinox sync api-spec.yml

Guides

Modular Schemas

For large APIs with 20+ endpoints, split your schema across multiple files:

  1. Create a main schema with global config (auth, groups, environments)
  2. Create domain modules with endpoint definitions only
  3. Reference them via includes in the main schema
# Project structure
api/
├── api-spec.yml          # Main schema with includes
├── includes/
│   ├── auth.yml          # Auth endpoints
│   ├── users.yml         # User endpoints
│   └── payments.yml      # Payment endpoints (prefixed)
└── dist/                 # Generated output

Included files can contain:

  • endpoints — merged into main endpoints list
  • auth — additional auth scheme definitions (merged)
  • environments — additional environments (merged)
Tip

Use the prefix field to add a path prefix to all endpoints from an include. Useful for versioning: prefix: /v2.

CI/CD Integration

Validate your API schema in CI pipelines to catch breaking changes early:

# .github/workflows/validate-schema.yml
name: Validate API Schema
on: [push, pull_request]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Download apinox
        run: |
          curl -sL https://github.com/denisetiya/apinox/releases/latest/download/apinox-linux-x86_64 -o apinox
          chmod +x apinox

      - name: Validate schema
        run: ./apinox validate docs/api-spec.yml --format json

Release workflow: Push a v* tag to trigger automatic builds for all platforms:

$ git tag v1.0.0
$ git push origin v1.0.0

The .github/workflows/release.yml workflow builds for Linux, macOS, and Windows (x86_64 + ARM64), attaches binaries to a GitHub Release.

FAQ

What's the difference between diff and migrate?

diff reads changelog entries inside the schema to show version-to-version changes. migrate compares two actual schema files to generate a migration guide — useful when you have separate files for v1 and v2.

Can I use JSON instead of YAML?

Yes. Apinox accepts both .yml and .json schema files. The format is auto-detected by file extension.

How do I mark a field as sensitive (passwords, tokens)?

Set sensitive: true on the field. In Postman collections, sensitive fields use type: hidden (field masked in UI). In OpenAPI output, they're marked with writeOnly: true.

Can I have per-endpoint server URLs?

Yes. Use the servers block on an endpoint to override the base URL for specific environments:

servers:
  production: https://api.example.com/v2
  development: http://localhost:9000

Why is my Postman collection empty?

You're likely using body: instead of examples: in your response definitions. Apinox expects examples: [{name: ..., value: ...}] format.

How do I update an existing Postman collection?

Use --collection-id to specify the existing collection ID, or set it in .apinox.toml. Apinox will update it in-place. You can also use --collection-name to auto-find and update.

Does Apinox support WebSocket or GraphQL?

Currently REST-focused. The schema format supports standard HTTP methods. WebSocket and GraphQL support are on the roadmap.

Where can I report bugs or request features?

Open an issue on GitHub Issues.
